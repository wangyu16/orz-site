# orz-site · design questions for the owner

**Decided 2026-10-21 (owner): all as recommended** (Q1 A with C for 0.1 until K1 ships; Q2 a; Q3 a; Q4 a, actions by major tag; Q5 a; Q6 a; Q7 a; Q8 a; Q9 a; Q10 a; the smaller defaults as in the spec).

Decisions [spec/site.md](spec/site.md) needs before step 9 (build). Each has
options and a recommendation (**→**). Spec sections in brackets.

| # | Question | Options | Recommendation |
|---|---|---|---|
| Q1 | **Where do links get the site's names?** (§4.2, §13 K1) | A. a kit option `twinLinks` (a naming pattern stored in `#orz-shell`, carried by save/update/verify like `includes`); kit → carriers 1.1 → orz-site. B. orz-site post-processes assembled HTML. C. family naming only. | **→ A**, and ship orz-site 0.1 with C if K1 is not ready (a non-family naming is then refused). B is impossible without breaking FC-18: links are rendered in the reader's browser from the text, so the file holds no `<a>` to rewrite; editing the island changes the document, an injection is undone by the first save and fails verify.html. A also closes D-113. |
| Q2 | **Which namings?** (§3.3) | a. family + per-kind file-name templates `{stem}…html`, same folder. b. also directory pages `x/index.html`. c. a naming function. | **→ a.** b moves the page a folder down and breaks its relative asset links (would need a `<base>` or link rewriting in the shell); Pages already serves `x.html` at `/x`. c cannot be stored in the file, so the published page could not follow it. |
| Q3 | **Config file format** (§3.1) | a. `orz-site.json` (+ JSON Schema). b. `orz-site.nyml`, flat `key: value`. c. YAML. d. a header in an `index.md`. | **→ a.** Nested data (per-kind pins and naming, glob lists), identical parse in Node and browsers with no dependency, schema validation and editor completion, readable by the workflow without orz-site. b is the family grammar but flat (lists and per-kind maps get awkward) and it is document metadata, which this is not; c adds a parser dependency; d mixes publishing config into a document. Cost of a: no comments. |
| Q4 | **How do the pins reach the installed carriers?** (§3.5, §8) | a. carriers are peer dependencies; the config pins exact versions; `init --github` writes them into the workflow's install line; `check` reports drift; `buildSite` refuses a mismatch. b. each orz-site release depends on exact carrier versions (pin = orz-site version). c. orz-site loads the pinned `-browser` bundles from jsDelivr in Node too. And: actions by major tag or by commit SHA? | **→ a**, actions by **major tag** (Dependabot-friendly; switch to SHAs if the owner prefers supply-chain pinning). b forces an orz-site release for every carrier patch and cannot move one kind alone; c puts a network loader into Node for no gain (the Node packages assemble the same bytes, FC-18 law 2). |
| Q5 | **Kind by folder?** Alembic and coursewerk store slides as `slides/<slug>.md`. (§2.2) | a. consumers rename to `<slug>.slides.md` in Phase 5; orz-site follows FC-18 (name decides). b. a config `kinds` glob map, allowed only when the naming gives every kind the same template (else family twin links point at the wrong name). c. honour the header's `carrier:` for plain `.md`. | **→ a.** b and c contradict FC-18 §3 and the kit's `twinHref`, which decides a link's target by its extension; the rename is a one-time `git mv` in a revision that is free to change (REBUILD Phase 5). Keep b as the fallback if Phase 5 resists. |
| Q6 | **Severity of a missing link or include** (§2.5, §4.1) | a. error by default, `"warn"` configurable. b. warning by default. | **→ a.** A published page with a dead link or an "Included file not available" note is a silent defect; a red build is caught before readers see it. Assets stay warnings. |
| Q7 | **Publish the texts and the manifest with the site?** (§3.2 `texts`, §6.1) | a. both published (`texts: true` default; `orz-site-manifest.json` at the root). b. texts off by default; manifest outside the deployed folder. | **→ a.** Each page already holds its full text, so publishing `x.md` exposes nothing new; it lets other sites include it (own-host includes) and readers fetch the source. The manifest is what a host (Alembic) or an incremental build reads from the live site. |
| Q8 | **Network includes from other hosts in CI** (§2.5) | a. allowed for `allowedHosts`, each body's SHA-256 recorded in the manifest; `--offline` refuses them. b. forbidden: vendor every include into the repository. | **→ a**, default `allowedHosts: []` (so a new site has none until the author lists a host). Determinism is then "given the same fetched bytes"; the manifest shows when a host changed. |
| Q9 | **Excluded files as include sources** (§2.2) | a. excluded = not published, still readable as file includes (`shared/` partials). b. excluded = invisible. | **→ a**, because partial texts are the main reason to exclude a `.md`; a host that must hide files leaves them out of the file map (route B) — orz-site never reaches beyond it. |
| Q10 | **The generated index** (§5) | a. an orz `md` document generated as text and assembled by the pinned orz-mdhtml. b. orz-site's own HTML template. c. no index (hosts write `index.md`). | **→ a**, mode `auto` (only when no document is `index.html`). It is themed by the kit, self-editing, deterministic, and adds no template code to keep in step with the carriers; c remains possible with `index.mode: "off"` (Alembic's hub). |

Also for the owner (smaller, defaults in the spec): whether empty texts are
